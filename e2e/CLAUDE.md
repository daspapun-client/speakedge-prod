# SpeakEdge — Project Guide for Claude

The Complete English Communication Ecosystem. API-first **modular monolith**:
FastAPI + MongoDB (Beanie ODM) backend, React + Vite SPA frontend. This file is
the map so you don't need to re-read the whole codebase each session — trust it,
but verify a specific file before editing it (code changes over time).

## Run / build / test

```bash
# Backend (Windows PowerShell) — venv lives at backend/.venv
cd backend; ./.venv/Scripts/python.exe -m uvicorn app.main:app --reload   # or ./run_dev.ps1
cd backend; ./.venv/Scripts/python.exe -m pytest -q                       # tests
cd backend; ./.venv/Scripts/python.exe -m app.db.seed                     # seed admin + demo codes (once)

# Frontend
cd frontend; npm run dev            # vite dev server
cd frontend; npm run build          # tsc -b && vite build  (run this to typecheck)
```

- Always invoke the backend Python via `backend/.venv/Scripts/python.exe` — the base system Python does **not** have the deps (beanie, fastapi, openpyxl…).
- `start.bat` / `stop.bat` at the repo root launch/stop both. Single-service prod: Docker build puts the SPA in `frontend_dist/` and FastAPI serves it (see `backend/app/main.py`).

## Architecture

- **Backend** `backend/app/`
  - `main.py` — app factory; registers every module router under `/api/v1` (see `MODULE_ROUTERS`). Mounts `/media`. Starts the scheduler.
  - `core/` — `config.py` (settings), `envelope.py` (`ok()` response wrapper), `exceptions.py` (typed errors + handlers), `rbac.py` (auth guards), `security.py` (JWT, `Role` enum, password hashing), `cache.py`, `ratelimit.py`.
  - `db/` — `base.py` (`AuditedDocument` base: soft-delete/archive lifecycle + `utcnow()`), `models.py` (**all** Beanie models + enums, ~780 lines — the single source of truth for data shapes), `mongo.py` (init/close), `seed.py`.
  - `modules/<name>/` — each has `router.py` (+ optional `service.py`). One domain per module.
  - `shared/` — `audit.py` (`log_activity`), `email_service.py`, `file_service.py`, `pdf_service.py`, `scheduler.py` (APScheduler: archive purge, scheduled-notification dispatch, orientation reminders), `messaging.py`.
- **Frontend** `frontend/src/`
  - `app/App.tsx` — all routes; `app/layouts/` — `PublicLayout`, `StudentLayout`, `AdminLayout`.
  - `features/<area>/` — page components (`public/`, `auth/`, `dashboard/` = student, `admin/`, `shop/`, `membership/`, `payments/`).
  - `lib/api.ts` — axios instance + `unwrap<T>()` (unwraps envelope, auto-refreshes on 401). `lib/auth.ts` — zustand `useAuth` store (persisted), `Role` type, `isAdmin()`.
  - `features/admin/_shared.tsx` — reusable admin UI kit: `PageHeader`, `StatCard`, `Paginator`, `Modal`, `StatusBadge`/`badgeClass`, `EmptyRow`, `fmtDate`/`rupees`, `downloadExport()` (authenticated blob download for CSV/XLSX).

## Backend conventions

- Every endpoint returns the envelope via `ok(data, message)` from `core/envelope.py`. Frontend unwraps with `unwrap()`.
- Guards from `core/rbac.py`: `require_admin`, `require_super_admin` (super-admin-only: archive restore/purge), `require_student`, `require_examiner`, `require_teacher`, `require_partner`. `require_role(*roles)` builds custom ones and lets super_admin through by default — **except the four portal guards, built with `allow_super_admin=False`**: an account reaches exactly one portal, so an admin is 403'd on student/teacher/partner/examiner endpoints just as a student is on admin ones (`tests/test_portal_isolation.py`). Admin surfaces that legitimately read another portal's data use their own `/admin/*` endpoint or an inline `user.is_admin` check (`_accessible_team`, `_accessible_batch`) — never a portal guard. Don't re-define a portal guard locally in a module; import it from `core/rbac.py`.
- Raise typed errors from `core/exceptions.py`: `NotFoundError`, `ConflictError`, `ValidationAppError`, `ForbiddenError`, `UnauthorizedError` (not raw `HTTPException`).
- Mutating admin actions call `log_activity(actor, action, role=…, target_type=…, target_id=…, meta=…)` (`shared/audit.py`) → visible in the Activity Logs page.
- **Archive-first soft delete**: models subclass `AuditedDocument` (`is_archived`, `archived_at`, `archived_by`, `delete_reason`, `auto_delete_at`). Use `.archive(by, reason)` / `.restore()`. 60-day retention, then the scheduler purges. Most list queries filter `is_archived == False`.
- Add new endpoints to the **existing** module router — don't create new modules casually.
- CSV/XLSX exports: `analytics/router.py` `_export_response(basename, header, rows, fmt)` streams CSV (default) or XLSX (`openpyxl`, in requirements).

## Frontend conventions

- Data fetching: `@tanstack/react-query` (`useQuery`/`useMutation`) + `api`/`unwrap` from `lib/api.ts`. Invalidate queries in `onSuccess`.
- Styling: Tailwind with shared component classes in `styles/index.css` — `card`, `btn-primary`, `btn-gold`, `btn-ghost`, `input`, `label`, `badge`. Brand colors: `brand`, `brand-light`, `brand-gold`, `surface`.
- Icons: `lucide-react` (type icon fields as `LucideIcon`, not a hand-rolled `ComponentType`).
- Admin pages follow the list + filters + detail/action-modal pattern; reuse `_shared.tsx` rather than re-implementing tables/pagination/badges.
- **Every guarded route group in `App.tsx` names its roles** — `<RequireAuth roles={['student']}>` for `/dashboard/*`, `roles={['teacher']}` for `/teacher/*`, `admin` for `/admin/*`, and so on; a wrong-role visitor is bounced to `homeFor(role)`. The only cross-portal group is `/dashboard/notifications` + `/dashboard/settings`, shared by student/teacher/partner/examiner (admin has `/admin/notifications`) — bare `<RequireAuth>` with no roles is the bug, not the default. `StudentLayout` is reused by four portals, so anything student-specific inside it (`TabBar`, the three popups) is gated on `isStudent`.

## Gotchas (learned the hard way)

- **Beanie serializes the document id as `id`, not `_id`** (`model_dump(mode="json")`, no `by_alias`). In the frontend always read `x.id` for the Mongo id used in action URLs. Using `_id` yields `undefined` → `/undefined/` requests.
- **Notifications router prefix is `/notifications` (plural)**; videos is `/videos` (plural). Most others are singular (`/membership`, `/partner`, `/teacher`, `/exams`, `/community`).
- Notification `recipient` supports `"*"` (all), group keys (`students`/`teachers`/`partners`/`examiners`), or a specific student_id/username. `scheduled_for` set → dispatched later by the scheduler (`sent=False` until then).
- Membership enrolment is **one-time** (the admission/membership fee is not re-charged), but **no facility is open-ended**: every benefit runs on the selected plan's own validity. The renewable entity is the `Subscription` (`expires_at`); "Renewal" extends the active subscription. **Never describe a membership or any facility as "lifetime" anywhere in the product** — state the plan's actual validity and entitlement instead.
- **Plan pricing (`PlanConfig`)**: checkout charges the **one-time admission/membership fee** (`offer_price` else `amount`) — `service._price_for` returns exactly that. `monthly_fee` is *quoted* on the plan card and collected separately (there is no recurring engine); the **only** way it joins the upfront charge is the buyer ticking "admission + first month" at checkout (`include_first_month`, default **on** wherever `monthly_fee > 0` — Silver through Diamond Pro; `service.first_month_fee` returns 0 on plans without one, so Tribe/Basic can never be over-charged). That choice rides on `Payment.first_month_included/first_month_amount` → `Subscription.first_month_included` (direct pay) or `ActivationCode.first_month_included` → the same field (guest bundle, set at activation). `prices` (`{month → paise}`) survives only as an optional per-term admin override and seeds **empty**. `months`/`durations` no longer affect price — they only set subscription validity (`_months_to_days`). Other tier dims: `classes_per_week` (teacher-led/week), `conversation_per_week` (= conversation *teams*), `community_years`, `support_years` (student relation support), `cefr_tests`, `speaking_tests`. Spec defaults live in `payments/service.py:PLAN_DEFAULTS`: missing keys are inserted, and rows below `PLAN_SPEC_VERSION` get their spec-owned fields **refreshed once** (bump the constant to push a catalogue revision to a live DB; admin edits stick until the next bump). Scheduler `send_subscription_expiry_reminders` nudges 1 month before expiry.
- **New Student Offer = a time-limited discounted *admission fee* on a shareable link** (`AdmissionOffer`, collection `admission_offers`) — for prospects who have not joined yet, and not to be confused with `Offer`, the dashboard pop-up for existing students. Admin mints one at Offers → New student offers (`POST /payments/admin/admission-offers`: plan + price + `valid_hours` from `service.OFFER_VALID_HOURS` = 24/48/72; the price must be **below** the catalogue admission fee), sends `/offer/<token>` themselves over WhatsApp/email, and can revoke it early (`DELETE …/{id}` archives it). `OfferLinkPage` resolves the token and forwards to `/checkout?plan=…&offer=<token>`; **expired, revoked and unknown tokens are all a 404** (`resolve_admission_offer`) → the visitor lands on `/plans` at the regular price, which is the whole "after expiry" behaviour. `POST /books/checkout` takes `offer` and `service.offer_admission_price` re-checks it server-side: it replaces the **admission fee only** (first month, book, GST, delivery untouched) and **raises** on a lapsed or wrong-plan token rather than quietly charging full price. A member with an active subscription is refused. `BookOrder.offer_token` + `record_offer_use` (called from `on_book_order_paid`) record whether the link converted. Tests: `tests/test_admission_offers.py`.
- **Dashboard exclusive offers (`Offer`, `/admin/offers`) are a quoted payable for an existing member.** "I'm interested" on a priced offer goes to `/checkout/membership?plan=…&offer=<id>`. `GET /payments/upgrade-quote?offer=` and `POST /payments/order` both take that id and `service.apply_member_offer` replaces the payable with `Offer.amount` (Silver at ₹500 means they pay ₹500, not the catalogue upgrade difference). A lapsed, wrong-plan or not-targeted offer **raises** rather than falling back to the standard fee. Tests: `tests/test_member_offers.py`.
- **`/plans` (`PlansPage`) is duration-free**: no 3/6/12 tabs. Cards render in a fixed order — `MAIN_ORDER` (Tribe → Basic → Silver → Gold → Diamond), then a separate "More Teacher-Led Learning" section for `PRO_ORDER` (Silver/Gold/Diamond Pro). Plans outside those lists (notably `Basic English Course`, sold under Books) are **not shown**. Monthly fee is the lead price where one exists, admission fee secondary; never combined. Benefit bullets are derived from the `PlanConfig` dims, so admin edits flow through — **except** the four that come with every tier (Live Orientation, CEFR-aligned certificate as per Speaking Test, instruction videos, multilingual instruction options). Those are not dims; they live in `frontend/src/lib/membership.ts` as `MEMBERSHIP_INCLUDES`. **`planBenefits(dims)` in that same file is the one benefit list in the product** — `/plans` cards, the checkout `OrderSummary` and the dashboard "Membership benefits" panel all render it, so they cannot drift (the dashboard used to carry its own hardcoded list advertising things unrelated to the plan the student bought; it now resolves the member's `PlanConfig` from `GET /payments/plans` and falls back to `MEMBERSHIP_INCLUDES` alone when the plan is not in the catalogue). Never say "lifetime" of a membership or of any facility anywhere in the product. **The dashboard shows the plan's own facilities and nothing else, on Limited Access as well as Full Access**: a learner is `Pending Verification` (Limited Access) from activation, but `_start_paid_subscription` gives them their `Subscription` at that moment, so `activePlan` resolves and the panel renders the same `planBenefits` list plus the same `SPEAKEDGE_BOOK_INCLUDED` chip the `/plans` card shows. On Limited Access the panel adds a note that facilities needing a verified membership are still restricted — the list is never trimmed, because the entitlement is real and only the access is pending.
- `POST /membership/activate` requires many form fields **and** three uploads (multipart): `photo`, `id_proof`, `education_proof`. The 5 consent fields are `consent_community_rules`, `consent_terms`, `consent_safety_policy`, `consent_non_refund`, `consent_process` — all still mandatory on the wire, but the learner now ticks **one** combined checkbox: `ActivatePage` (and the admin enroll modal in `AdminCodes`) sets all five from it and disables the submit button until it is ticked. `ACTIVATION_CONSENTS` is now just the list of field names. `consent_guardian` is a **separate sixth** consent, required only for under-18s. `whatsapp` is **optional**; `phone` stays required.
- **There is no `age` field on the registration form — `dob` is required and age is derived** (`age_from_dob`, IST). Age then drives everything: `< MIN_MEMBERSHIP_AGE` (8) is refused outright; `section_for_age` puts 8–15 in Kids and 16+ in Adults; `< MINOR_AGE` (18) makes the parent/guardian block mandatory, so 16–17 year-olds sit in the Adult Section but still go through parental consent. `Student.age` is still stored (derived) because the community profile and filters read it. `POST /membership/resubmit` takes `dob` (not `age`) and re-runs both rules.
- **`validated_registration()` in `membership/router.py` is the one validator for the registration form** — it checks DOB/eligibility/allowlists, stores the three uploads and returns the `activate_membership` kwargs. Both `POST /membership/activate` and admin `POST /activation-codes/manual-activate` call it, so a new form field is added in exactly one place.
- **Academic / educational background** is `education_level` (required, allowlisted by `ACADEMIC_LEVELS`) + a required `education_proof` upload (`file_service.save_education_proof` → `/media/education_proofs/`). Like `id_proof_url`, it is **private**: both are excluded from the bulk `GET /admin/students` payload and appear only on the admin single-student views; nothing member-facing reads the `Student` doc (the community directory reads `CommunityProfile`).
- **Policy pages**: `/privacy`, `/terms`, `/faq`, plus `/community-rules`, `/safety-policy`, `/refund-policy` — all in `features/public/LegalPages.tsx`; `/contact` is its own `features/public/ContactPage.tsx` and is what the nav + footer "Contact" links point at. All linked from the footer and from the activation consent block. Content is drafted from how the platform actually works and still needs a legal review.
- **Public contact details live in `frontend/src/lib/site.ts`** (`CONTACT_PHONE`, `WHATSAPP_URL`, `SUPPORT_EMAIL`, `OFFICE_ADDRESS`, `SUPPORT_HOURS`) — the footer, `/contact` (`ContactPage.tsx`) and the legal pages all read them from there, so there is no second copy of the phone number or support address.
- **Google Business Profile + social media links are admin-editable, not hard-coded** — the real URLs only exist once SpeakEdge is live, so they are stored in the DB (`SiteLinks`, a singleton with `links: [{key, label, url}]`, collection `site_links`) and edited at Admin → Site Links (`AdminSiteLinks.tsx`) with no code change and no deploy. `modules/site/router.py` serves `GET /site/links` (**public** — the footer renders for anonymous visitors, and it returns only rows whose `url` is set, so a blank placeholder never ships a broken link) plus `GET`/`PUT /site/admin/links` (admin: every row, including the blank ones). Seeded on first read with `DEFAULT_LINKS` (gmb, facebook, instagram, youtube, linkedin, x) — admin may add a row with any `key`, and `SOCIAL_ICON` in `PublicLayout` falls back to a globe for one it doesn't know. A URL not starting with `http(s)://` is a 422. Frontend reads it through `useSiteLinks()` in `lib/site.ts`; the `PUT` invalidates the `site-links` query. Tests: `tests/test_site_links.py`.
- **Free demo** (`/demo` → `POST /leads/demo`): full registration form — name, phone, optional email, **age**, education, occupation, one of three fixed weekly slots, a **preferred date on that slot's weekday**, what they want to improve (optional), attribution, and a **mandatory privacy consent** (`consent_privacy`). All allowlists (`DEMO_SLOTS`, `EDUCATION_OPTIONS`, `OCCUPATION_OPTIONS`, `HEARD_FROM_OPTIONS`) live only in `leads/router.py` and are served by `GET /leads/demo/options` — `DemoPage.tsx` renders whatever that returns, so there is **no list to keep in sync** any more. That endpoint also returns each slot's next `DEMO_DATE_CHOICES` bookable dates, so the date picker can only offer dates the server will accept.
  - The first word of each `DEMO_SLOTS` label is the weekday and is load-bearing — `demo_date` is validated against it. Keep new slots in the same "Weekday time–time" shape.
  - **Dates are IST** (`today_ist()`): using UTC would offer a same-day slot to anyone booking before 05:30 IST.
  - `Lead.demo_group` is **derived from age, never asked** — `demo_group_for_age()` splits at `KIDS_MAX_AGE` (14, inclusive → Kids) and returns `PromptAudience` values so a converted lead lines up with the Kids/Adults course.
  - Everything is shown in Admin → Leads (list + detail modal) and the CSV/XLSX export.
- **Exam slots are set weekly — weekday + time, not a date.** `ExamSlotRule` is the thing admin manages (`kind`, `title`, `day_of_week` lowercase weekday, `time_of_day` `"HH:MM"` **IST**, `duration_minutes`, `capacity`, `examiner_id`): "Sunday – 11:00 AM", repeating every week until changed or removed. `modules/exams/service.py` materialises it into ordinary bookable `Exam` rows over a rolling `SLOT_HORIZON_WEEKS`=8 horizon, each stamped `Exam.rule_id`, so bookings, examiner scoping, reports and notifications never learn about recurrence. Admin CRUD is `GET/POST /exams/admin/slot-rules`, `PATCH`/`DELETE /exams/admin/slot-rules/{id}`; a duplicate (kind, day, time) 409s. An `Exam` is "in use" when somebody holds a live seat on it (`service.booked_slot_ids`).
- **`app/shared/weekly.py` is the one implementation of "repeats every week"**, used by exam slots and orientation sessions. A rule needs `id` / `day_of_week` / `time_of_day`; an occurrence model needs `scheduled_at` + `rule_id`. `WeeklySchedule(doc_cls, build=..., in_use=...)` supplies `generate` / `rebuild` / `drop_future` / `purge_past` / `sync`; each module only says how to build an occurrence and what makes one untouchable. Three rules live there because they are easy to get wrong — don't re-derive them per module:
  - **An occurrence in use is never touched.** A rule edit re-cuts only the *free* future ones; the response reports how many were kept (`booked_slots_kept` / `enrolled_sessions_kept`).
  - **A cancelled occurrence stays cancelled.** `generate` treats archived dates as taken, so a single sitting called off by hand doesn't reappear on the next scheduler pass.
  - **`rebuild` deletes rather than archives** the placeholders it replaces — an archived row at the same time would block its own replacement (which is why an edit that leaves the day/time alone can still re-cut at those same times). `drop_future` (rule removal) archives instead, as a trace of the withdrawal.
- Scheduler job `roll_weekly_slots` (6-hourly) calls both modules' `sync_all()`: it walks the horizon forward and archives generated rows that passed unused (`DEFAULT_GRACE_DAYS`=7). `POST /exams/slots/bulk` survives for one-off dated sittings outside the weekly rhythm.
- **`Exam` is still the unit everything downstream works on**: `kind` + `title` + `scheduled_at` + `duration_minutes` (default 20) + `capacity` (default 1, a 1:1 oral test) + `examiner_id` (= the examiner's `User.username`, which is also their JWT `sub`). `AdminExams.tsx` has a tab each for **examiners** (`GET/POST /exams/admin/examiners`, `PATCH /exams/admin/examiners/{username}`) → **weekly slots** → **exam dates** (the generated rows + `POST /exams/{id}/assign`, which notifies the examiner and everyone already holding a seat). `GET /exams/` resolves each slot's `examiner_name`/`examiner_whatsapp`/`seats_left`/`ends_at`; `?upcoming=true` drops past slots, `?bookable=true` also drops full ones. Booking rejects a past slot, a duplicate, a full slot and an exhausted plan quota. `DELETE /exams/{id}` archives one date but is refused once anyone has booked it.
- **Every slot/session time on the wire is an explicit UTC instant** (`_iso()` in `exams/router.py`, `orientation/router.py` and `orientation/service.py`) and every one in notification copy is IST (`_when()`). A naive ISO string is read as browser-local by the frontend and lands 5.5 hours out — that is why `service.to_utc` / `to_ist` / `to_naive_utc` exist and why `/exams/slots/bulk` reads its `dates`×`times` grid as IST. Slot rows created before this (bulk-created, stored as IST wall-clock in a naive field) now read 5.5 h early; re-cut them from a weekly slot rather than trusting the old time.
- **Examiner contact details live on `User`** (`phone`, `whatsapp`) — set by admin from Exams → Examiners, and published to students on every slot that examiner is assigned to. There is no separate Examiner model.
- **Every examiner endpoint is scoped to that examiner's own slots.** `_assigned_bookings()` in `exams/router.py` starts from `Exam.examiner_id == examiner.subject`, so `/exams/examiner/assigned`, `/examiner/students` (the spec's "search students"), `/examiner/slots`, `/examiner/summary` and `/examiner/reports` can never reach another examiner's work, and `POST /exams/report` 403s when the booking's slot is not theirs. An examiner is deliberately *not* given a directory of the whole student base.
- **Partner numbers all come from `modules/partner/service.py`, and only *approved* reports count.** A `PartnerReport` is `pending` until an admin reviews it; `service._approved()` is the single gate, so the partner dashboard, admin overview and every export agree by construction. Monthly/yearly buckets key on `PartnerReport.occurred_on` (the date the sale happened) and fall back to `created_at` — never on the review date.
- **A partner may only sell what admin allowed them.** `_check_product` validates a lead's `interest` and a report's `product` against `Partner.products_allowed`; `_active_partner`/`_partner_for` refuse every write unless the account is `approved` **and** the record is the caller's own. A suspended partner keeps read access to their dashboard so they can see why.
- **`PartnerLead.history` is an append-only status trail** written by `PATCH /partner/leads/{id}` (and seeded on creation) — that is the "View Lead History" panel. `source` is `partner` or `microsite`.
- **Franchisee microsites (Part E) are admin-managed content on the `Partner` row** — `about`, `address`, `gallery`, `logo_url`, `map_embed_url`, `public_products`, `microsite_slug`, `microsite_published`. Public URL is `/franchisee/<slug>` (`/partners/<slug>` still resolves); `GET /partner/microsite/{slug}` **404s unless published**, and so does its enquiry form. `POST /partner/microsite/{slug}/enquiry` (rate-limited, public) files a `PartnerLead` into that franchisee's own list — that is what "link leads to the franchisee dashboard" means. Microsites are refused for any partner type other than `Complete Sujyoti Franchisee Partner`.
- **`Partner.public_products` empty means "show everything allowed"** — visibility control is opt-in so there is never a second product list to keep in sync. `_public_partner()` is the only serialiser for public payloads and strips `username`/`remarks`/`consent_contact`/`products_allowed`.
- **Every customer-facing PDF carries the brand mark.** `pdf_service.draw_logo` renders `app/shared/assets/speakedge-logo.png` (a copy of the frontend `logo-icon.png`) in a white rounded tile; `_header` puts it beside the wordmark on the invoice, receipt and CEFR report, and the certificate gets it centred above the title. It degrades to text if the asset is missing, so never let a missing file fail a document.
- **One receipt design, seven transaction types**: `pdf_service.payment_receipt_bytes` (the "PAYMENT / ORDER RECEIPT"). The governing rule is *only information relevant to that transaction appears* — `student_id` is omitted for guests and for plain book buyers, `delivery` only where something physical moves, `extra_meta` carries type-specific rows (previous/upgraded membership), and `total_label` varies ("Amount Paid for Upgrade"). `RECEIPT_TYPES` names the transaction on the document and `RECEIPT_NOTES` (via `receipt_note(key, **fields)`) supplies the closing heading + body, some with `{placeholders}`: `new_membership`, `membership_upgrade`, `membership_renewal`, `monthly_class`, `monthly_class_restart`, `book_purchase`, `general`. A monthly fee reads as **Resumed** rather than Confirmed when its `due_month` is earlier than the month it was paid in — access had lapsed. Two builders feed it: `book/service.build_receipt(order)` (New Membership, or Book Purchase when the order has no plan — no membership/Student ID/activation on that one) and `payments/service.build_payment_receipt(payment)`, which **delegates to the order one whenever the payment has a `BookOrder`** so there is never a second thinner document for the same money. Served by `GET /books/receipt/{order_number}?phone=` (guest, phone-checked) and `GET /payments/receipt/{payment_id}` (student-scoped — another student's payment 404s); the dashboard Payments page downloads the latter as an authenticated blob via `downloadExport`. Rendered on demand, never persisted, so it works before payment is reconciled. **`generate_invoice` is a separate document and stays that way** — it is the GST tax invoice (`SELLER_GSTIN` → "TAX INVOICE") and must not be folded into the receipt.
- **A membership upgrade costs the difference between the two tiers' *standard* prices** (`payments/service.upgrade_quote`): credit = the current plan's catalogue `amount`, charge = the new plan's catalogue `amount`. Deliberately **not** `_admission_for`/`_price_for` — a discount the learner once received (an admission-offer link, a promotional `offer_price`) must never move the upgrade price in either direction. Applied only when the new tier costs *more* — renewing the same plan or moving to a cheaper one gets nothing, or a renewal would cost ₹0. `create_order` nets it off, stamps `Payment.previous_plan` / `upgrade_adjustment` (so the receipt shows fee → credit → paid without recomputing), and **forces `delivery_type=None` and `include_first_month=False`**: no second SpeakEdge Book is issued on an upgrade, so no book, delivery or first-month line may appear on it. `GET /payments/upgrade-quote?plan=` drives `MembershipCheckoutPage`, which hides the book, the delivery block and `FirstMonthChoice` when `is_upgrade`.
- **A plan change never restarts benefits, and `service.switch_plan` is the one place a membership is swapped over** (upgrade, downgrade and the scheduler all go through it). Passing `carry=<the membership being left>` copies `Subscription.benefits_start_at` — the *first* membership start — onto the new row and counts the new tier's validity from it, so a Basic member six months in who upgrades to Diamond has 4y6m of the 5-year community access left, not 5 fresh years. Counted entitlements need no arithmetic: eligibility is the new tier's total and `exams._eligibility` already deducts every test ever booked. `billing_start_at` + `monthly_reminders_sent` carry too, so the monthly cycle is never re-anchored. A **renewal** passes no `carry` and does start a fresh window — inheriting a nearly-spent year there would be the bug.
- **An upgrade may be dated: the learner picks an activation date up to `UPGRADE_ACTIVATION_DAYS` (30) out** (`activate_on` on `POST /payments/order`; blank = immediately). A dated upgrade is *parked* on the membership already held (`Subscription.pending_plan` / `pending_plan_at` / `pending_payment_id`, set by `_apply_subscription_payment`) and that membership runs untouched until the day — which is what the **Important Upgrade Notice** on the checkout page promises before any money moves. Scheduler job `apply_plan_changes` (hourly → `service.apply_due_plan_changes`) performs the switch.
- **Downgrades are Pro → own standard tier only** (`service.DOWNGRADE_PATHS`: Silver/Gold/Diamond Pro → Silver/Gold/Diamond — 2 teacher-led classes a week become 1). Free, so no payment and no activation-date choice: `POST /payments/downgrade` parks it on the same `pending_plan` fields for the **next monthly cycle** (`_next_cycle_date`), and the Pro benefits run out the cycle already paid for. `GET /payments/plan-change` serves both the scheduled change and the downgrade on offer (`PlanChangePanel` on `/dashboard/subscription`); `DELETE /payments/plan-change` cancels a pending downgrade but **409s on a paid upgrade** — that one is a refund, which admin handles. Tests: `tests/test_plan_changes.py`.
- **`kind="general"` is the catch-all payment** — miscellaneous money that fits none of the other categories. Admin records it as already-collected via `POST /payments/admin/general` (Payment Management → "Record a payment"), and `Payment.purpose` — chosen from `service.GENERAL_PAYMENT_PURPOSES` (a shortlist served by `GET /payments/admin/general/purposes`, *not* an allowlist; "Other" lets admin type their own) — is what the receipt and the invoice print as the description. It settles on creation through `_fulfil`, so the student can download the receipt immediately.
- **Exports are CSV / XLSX / PDF via `app/shared/exports.py`** (`export_response`; `analytics/router.py` aliases it as `_export_response`). Partner side: `GET /partner/me/export?dataset=leads|sales|monthly|yearly|product`. Admin side: `GET /partner/admin/export/{partners|leads|sales|admissions|product|monthly|yearly}`. PDF uses reportlab via `table_pdf_bytes`.
- **`CORPORATE_PARTNER_URL` in `frontend/src/lib/site.ts` is an empty placeholder** — the spec routes SpeakEdge's Partner links to the Sujyoti EdTech corporate page. `partnerHref()` falls back to the in-app `/partners` directory until a real URL is set, and `HomeHashLink` renders an `http(s)` target as an external `<a>`.
- **`CEFRReport` and `Certificate` share `ExamResultBase`** (`exam_id`, `exam_title`, `exam_date`, `examiner_id`, `examiner_name`, `remarks`) so the two admin result views can list Exam Date / Student ID / Examiner Name / Level-or-Grade / Remarks off one shape. `exam_date` and `examiner_name` are **copied off the slot at submission** — the result outlives the slot row. `Certificate.grade` is a real field now, not just words inside `title`. A booking can only be reported once (`ConflictError`), and the result rides back on `GET /exams/my-bookings` (`result`) plus `GET /dashboard/downloads`.
- **Monthly fees have no billing engine — only a derived due schedule** (`modules/payments/monthly.py`). Due dates = `Subscription.started_at` + n calendar months (day clamped to short months), while `PlanConfig.monthly_fee > 0` and the date is before `expires_at`. A month is settled by a paid `Payment(kind="monthly", due_month="YYYY-MM")` — **except month 1 when `Subscription.first_month_included`**, which was paid on the admission order and so has no monthly `Payment` to match: `due_dates` simply starts at month 2 for those. `GET /payments/monthly-due` returns the next unsettled month (overdue ones keep coming back) with `reminder_active` true from `REMINDER_DAYS`=3 out; `POST /payments/monthly-order` starts the gateway order. `MonthlyDuePopup` (mounted in `StudentLayout`) shows Due Date + Amount Due + Pay Now and collapses to a persistent bar — never fully dismissible until paid. Scheduler job `send_monthly_payment_reminders` raises one notification per due month (deduped via `Subscription.monthly_reminders_sent`).
- Payments admin actions (`manual-approve`, `refund-status`) key off `razorpay_order_id`; manual/book payments may lack it.
- **Fulfilment is claimed atomically, never read-then-written** — `payments/service._claim_for_fulfilment` moves the Payment into `paid`/`manually_approved` with a conditional update and only the winner runs `_fulfil`. `/payments/verify`, `payment.captured` and `order.paid` all land within the same second, so without it one order produced two invoices and two active Subscriptions. Any new path that fulfils a payment must go through the claim.
- **Refunds actually call the gateway.** `payments/service.refund_payment` posts to Razorpay first and only then records `refunded`/`partially_refunded`; `set_refund_status` routes the two terminal statuses through it (a partial refund must carry `amount` in paise) while the earlier lifecycle states are record-only. Payments taken outside the gateway (manual approval, demo orders) are recorded as settled by hand. `refund.created`/`refund.processed` webhooks reconcile refunds issued from the Razorpay dashboard, and `payment.failed` marks the attempt `failed` (never touching an already-paid record) — subscribe to all of them.
- **Membership + Book is one order, one payment.** Exactly one `BookProduct` carries `is_speakedge_book` (admin ticks it; `book/service.clear_other_speakedge_books` unflags the rest, `GET /books/speakedge` resolves it). That book can only be bought with a plan and vice versa — both entry routes (`/plans` → Subscribe, and `/shop` → SpeakEdge Book → `/plans`) land on `/checkout?plan=`, which posts `plan` (+ a defaulted `months=12` for validity only) to `POST /books/checkout`. The `Payment` stays `kind="book"` (plan + months set) so **no `Subscription` is created at payment**: the plan is stamped on the reserved `ActivationCode` (`plan`, `plan_months`) and `membership/service._start_paid_subscription` turns it into the first Subscription at activation. Guests have no session, so `/payments/verify` (student-only) is not their path — they use `POST /books/verify-payment` (order number + phone), which returns the `activation_code` so the confirmation screen can link straight to `/activate?code=`; the webhook and admin `manual-approve` stay as backstops. Other books keep the plain `/shop/product/:id` flow. `GET /books/receipt/{order_number}?phone=` streams the confirmation PDF (phone must match; rendered on demand, so it works before payment is reconciled).
- **An activation code is reserved only when the order carries a `plan` *and* the payment is `kind="book"`** (`book/service.on_book_order_paid`). A plain Sujyoti book must not consume one — the buyer would find it on the tracking page and get a free membership out of a ₹150 book, and the pool would drain. Nor may a member's own order: a `kind="subscription"` payment has already created their Subscription in `_fulfil`, so a code there would be a second free membership. Codes themselves are **pre-generated in batches by admin** (`POST /activation-codes/generate`, `SPK-26-XXXXXX`); checkout only claims one from the unused pool with a conditional update. The record is Admin → Activation Codes (filter `reserved`, and the row shows the plan + who activated it) and Admin → Book Purchases (the code on the order).
- **Book stock is held from checkout, not from payment** — `create_checkout` reserves the copy and sets `BookOrder.stock_reserved`, which is the one flag every release path checks (ship, office collection, cancel, expiry). Two buyers can therefore no longer both pay for the last copy: the second checkout 409s. The cost is that abandoned carts hold stock, so the scheduler job `book/service.expire_abandoned_orders` (every 30 min) cancels unpaid orders older than `ORDER_PAYMENT_WINDOW_HOURS` (48) and releases them. `POST /books/resume-payment {order_number, phone}` reopens an abandoned order with a fresh gateway order id on the same `BookOrder`/`Payment` — a Razorpay order id is single-attempt, so the old one cannot be reused. Surfaced as "Pay now" on `/track`.
- **`GET /books/my-orders`** (student) lists the caller's own book orders, rendered at the bottom of `/dashboard/payments`. `POST /books/checkout` stays public but reads an optional bearer token, so a signed-in student's order is filed under their id instead of `guest:<phone>`.
- **`/shop` header copy is spec-fixed**: heading "Book Shop — Sujyoti Publications", subtitle "Explore books from Sujyoti Publications." — no activation-code blurb. The **menu** label is "Our Books & Other Courses" (nav + footer, both → `/shop`); the page heading is deliberately not the same string. `BookProduct.description` is admin-managed (Admin → Books, both the add and edit modals) and renders on the shop card, the product page and the checkout summary.
- **`is_speakedge_book` is the only thing that decides a purchase route, and reading about a title is never gated on it.** Every shop card carries a "Read About This Book/Course" link to `/shop/product/:id` — including the SpeakEdge Book, which sorts **first** in `GET /books` (the router sorts the flagged product to the front). What the flag switches is the *purchase* action alone: flagged → `/plans` (Membership Plans), unflagged → the product page's own direct-payment form. `ProductPage` therefore no longer redirects the SpeakEdge Book away; it renders the full description and swaps the checkout `<aside>` for an "Included with membership" panel linking to `/plans`, so the buy form simply does not exist on that page. Adding a future book or course needs no code change. Home page: "Get Your SpeakEdge Book" goes to `/plans`, never to `/shop`.
- **The SpeakEdge Book is included in the membership fee and is never charged on top of it.** A membership order ships the copy (inventory held, `BookOrder` filed, delivery choice intact) with `book_amount = 0` and `gst_amount = 0` — zeroed in `payments/service._book_quote` for a member's order and in `book/service.create_checkout` for the guest bundle, so the order response, the `BookOrder`, the invoice's GST breakup and the receipt all follow from one place. `build_receipt` prints that line as **Included** rather than 0.00 (`pdf_service.payment_receipt_bytes` accepts a `str` amount for exactly this). Delivery is a real cost and is untouched: home delivery still charges `BOOK_DELIVERY_CHARGE_PAISE`, office pickup is free. Anything asking "does a copy ship?" therefore keys off `product_id`, never the price — `ships` in `create_checkout`, the activation-pending branch in `on_book_order_paid`, the invoice item in `_fulfil`, and `has_book` on `GET /books/my-orders` (a ₹0 book read as "membership-only" would silently never be dispatched). The order detail in `AdminBooks` reads "Included with membership" on that row for the same reason. A book bought on its own from `/shop` is priced from the catalogue as before.
- **A guest checkout with a plan and no product is a membership-only order** — when no `BookProduct` carries `is_speakedge_book`, `/checkout` no longer dead-ends ("The SpeakEdge Book is unavailable"): it renders membership-only (no book card, no delivery choice, address kept as billing) and posts `/books/checkout` without `product_id`. `book/service.create_checkout` then charges `book_amount=0` + no delivery/GST (the legacy flat `BOOK_PRICE_PAISE` fallback only applies to a *book* order with no plan), and `on_book_order_paid` pushes straight to `Membership Activation Pending` with a reserved activation code — no inventory, no pickup OTP. The bundle is unchanged whenever a SpeakEdge Book exists. The same fallback covers a SpeakEdge Book that is **out of stock**: `/checkout` drops the book rather than disabling the button, so an inventory problem never blocks new memberships.
- **Both Subscribe buttons on `/plans` go to a checkout page** — guests to `/checkout` (the membership + SpeakEdge Book bundle), signed-in members to `/checkout/membership` (`MembershipCheckoutPage`). Both now sell the same bundle: `POST /payments/order` takes `delivery_type` (`home`/`office`) and `service._book_quote` puts the SpeakEdge Book on the order and prices `BOOK_DELIVERY_CHARGE_PAISE` onto it, holds the copy from checkout, and `book/service.create_membership_shipment` files a `BookOrder` against the *subscription* payment (so `_fulfil` looks up a book order for **every** kind, not just `kind="book"`). No book configured or out of stock → `_book_quote` returns None and it is membership-only, exactly as `/checkout` degrades; omitting `delivery_type` does the same. `billing` (`Payment.billing`, model `BillingDetails`) doubles as the delivery address and `service._save_billing_to_profile` copies the non-empty parts onto the `Student`. Price is still server-side only — the order response returns the breakdown (`plan_amount`/`first_month_amount`/`book_amount`/`gst_amount`/`delivery_charge`) purely for display. On success the Subscription already exists (`_fulfil`), so the page confirms and sends the member to `/dashboard`.
- `features/payments/checkout.ts`: `startSubscriptionCheckout()` returns `{paid}` and throws a user-facing message (for pages that render errors inline); `startCheckout()`/`startMonthlyCheckout()` wrap it with `alert()` for the one-click flows (offer acceptance, monthly-due popup).
- **Razorpay has two modes, switched by `payments/service.keys_configured()`** (key id starts with `rzp_` and has no `xxxx`). *Demo*: no gateway call, ids are `order_test_*`, `/payments/verify` skips the signature — the frontend mirrors the same rule (`isDemoOrder` in `features/payments/checkout.ts`, `testKeys` in `shop/bookCheckout.ts`) and self-verifies. *Live*: real orders, and a gateway error now **raises** instead of falling back to a test order (a fallback would have been treated as pre-paid). Signature checks are only bypassed for `verify_and_activate(..., trusted=True)`, used by the webhook, whose body HMAC is checked first. `tests/conftest.py` forces demo mode so a real key in `.env` never makes tests hit the network.
- **The webhook fails closed until `RAZORPAY_WEBHOOK_SECRET` is a real value** (`service.webhook_configured()` rejects empty and the shipped placeholder `webhook_secret`). It is the only caller that skips the per-order signature, so a publicly-known secret would let anyone forge `payment.captured` and mint a free membership + activation code. Both `payment.captured` and `order.paid` are accepted (`_PAID_EVENTS` in `payments/router.py`) — subscribe to both in the dashboard, plus `payment.failed` (`_FAILED_EVENTS`) and `refund.created`/`refund.processed` (`_REFUND_EVENTS`). Guest book orders reconcile through this hook or admin `manual-approve`.
- **The client never prices anything.** `POST /payments/order` takes only `plan` / `months` / `accept_terms` and always books `kind="subscription"` at the `PlanConfig` price; a body carrying `amount` or `kind` is ignored. `/payments/verify` is scoped to the caller's own order (a payment belonging to another student 404s, so nobody can push it through or park it in `failed`). See `tests/test_payment_gateway.py`.
- **The invoice prints a tax breakup only once `SELLER_GSTIN` is set.** `payments/service._apply_gst` fills `Payment.taxable_amount/cgst/sgst/igst/total_tax` from the book order's `gst_amount` (CGST+SGST when the buyer's state matches `SELLER_STATE`, else IGST) and `pdf_service.generate_invoice` titles the document "TAX INVOICE"; with no GSTIN it stays "INVOICE" and says the price is tax-inclusive — printing a breakup without a registration would be a false tax invoice. Guest invoices show the buyer's phone, never the internal `guest:<phone>` key.
- **Activation hands the guest order over to the new account** — `membership/service._start_paid_subscription` re-points `BookOrder.student_id` and `Payment.student_id` from `guest:<phone>` to the real student id and stamps `Subscription.payment_id`. Without it the buyer could never fetch the invoice for their own membership, since payment reads are student-scoped.
- The whole suite passes. `tests/conftest.py` clears the in-memory rate-limit counters before every test — they are process-local, so without it a login-heavy test file 429s an unrelated one.
- **Kids and Adults are separate courses, now allocated from the learner's age** (`section_for_age`), not from the activation code. `ActivationCode.audience` is still set by admin at generation (`POST /activation-codes/generate {count, audience}`; `POST /activation-codes/audience` re-points an *unused* code, refused once activated) and still records which course was *sold*, but it is only the fallback when activation supplies no derived section. `Student.audience` is deliberately **absent from `ProfileUpdate`** in `student_dashboard/router.py` — a student sending it is ignored — so after activation only `PATCH /admin/students/{id}` can move someone between courses. Everything downstream (prompt library `/me/*`, AI sessions) resolves lessons from `student.audience`.
- **`GET /membership/form-options` is the single source of truth for the registration form's lists.** It serves `id_proof_types`, `academic_levels`, `guardian_relationships`, `cefr_levels` and the age rules (`min_age`, `kids_max_age`, `minor_age`), plus `audience` when a `code=` is passed. `ActivatePage.tsx` consumes it via the exported `useActivationOptions()` hook and **hardcodes no lists** — `AdminCodes.tsx`'s enroll modal reuses the same hook plus the exported `GuardianFields` / `SectionNotice` / `ageFromDob` / `sectionFor`, so there is nothing to keep in sync any more.
- **ID proof is the document *type* plus the upload, and no document number is ever collected.** `id_proof_type` (required, allowlisted by `ID_PROOF_TYPES` in `membership/router.py` — masked Aadhaar, Voter ID, PAN, DL, Passport, School/College photo ID, other government photo ID) + the required `id_proof` file. The old `id_proof_number` field was **removed everywhere** (model, both activation routes, `ActivatePage`, the `AdminCodes` enroll modal, and the two admin views) — the number is not needed for activation-code generation or activation, so don't reintroduce it. Shown in the verification queue and the admin student profile only.
- **Forgot password is stateless — there is no reset-token collection.** `POST /auth/forgot-password {username}` -> `auth/service.request_password_reset` mails a link to `PUBLIC_BASE_URL/reset-password?token=…`; `POST /auth/reset-password {token, new_password}` (min 8 chars) sets it. The token is a JWT signed with `SECRET_KEY` **plus the user's current `password_hash`**, so completing a reset (or any other password change) re-keys it and every outstanding link stops verifying — that is what makes it single-use, with nothing to store, expire or purge. Expiry is `PASSWORD_RESET_EXPIRE_MINUTES` (60). It works for **every role**: `find_login_user` accepts a student_id, a staff username or an email. Forgot-password is deliberately **silent about whether the account exists** — same 200 and same message either way, so it can't be used to enumerate accounts — which means the frontend can never say "no such user"; it always shows "check your email". An account with no `email` (student email is optional at registration) simply gets nothing: admin resets those by hand via `POST /admin/users/reset-password`. Pages: `features/auth/PasswordResetPages.tsx` (both steps), linked from `LoginPage`. Tests: `tests/test_password_reset.py`.
- **Access locks** (`shared/access.py`): `Student.teacher_class_locked` / `community_locked` / `access_lock_reason`, set via `POST /admin/students/{id}/access`. Enforced by the `require_unlocked_teacher_student` / `require_unlocked_community_student` guards, which have **replaced `require_student` throughout `teacher/router.py` and `community/router.py`** — use those guards for any new student endpoint on those surfaces. The two WebSockets authenticate from a query token and so check `_community_locked()` inline instead. A lock is not a suspension: the rest of the account keeps working.
- **The monthly-fee schedule is anchored to `Subscription.billing_start_at`** — the student's first teacher-led class, set by admin via `POST /payments/admin/class-start/{student_id}` (`GET` on the same path returns the current value plus a `suggested_class_start_date` = earliest `Batch.class_dates` entry the student is enrolled in). `monthly.billing_anchor()` falls back to `started_at` when it is unset, so pre-existing subscriptions keep their old dates. Saving a new date clears `monthly_reminders_sent` so reminders re-arm against the new months.
- **No payment can be started without accepting the Terms.** `POST /payments/order` and `POST /books/checkout` both require `accept_terms: true` and stamp `Payment.terms_accepted_at` / `terms_version` (`settings.TERMS_VERSION` — bump it when the policy pages are revised). The monthly-fee order inherits the acceptance from the original purchase rather than asking again. Frontend: `components/TermsAgreement.tsx` exports `TermsAgreement` (inline block for forms — checkout, product page) and `TermsGateModal` (dialog for flows that jump straight to the gateway — plan renewal, accepting a priced offer). The block is **only** the acceptance checkbox linking Terms / Privacy / Cancellation & Refund — the policy summary bullets that used to sit above the Pay button are gone by request; put policy text on the pages in `LegalPages.tsx`, not in the payment window.
- **The admin prompt library day panel is a local draft with an explicit "Save day" button** — it no longer autosaves on blur. `LineListEditor` keeps blank lines while typing and they are stripped on save. The prompt-body editor keeps its own separate "Save prompt" button.
- **`Video` carries both videos and PDFs** (`kind: "video" | "pdf"`, default `"video"`). Collection is still `videos` and the router is still `/videos`; the student UI splits them (`/dashboard/videos` vs `/dashboard/study-material`) by passing `?kind=`. Membership gating for both lives in `shared/content_access.py` — `modules/video/router.py` imports it under the old private names (`_visible_to_student`, `_student_plan`) so existing tests/imports keep working.
- **Prompt library never materialises 2,880 prompts.** `PromptTemplate` (~10 docs: one per audience × slot) holds the reusable body with `{{placeholders}}`; `PromptLesson` (one per audience/week/day, created lazily) holds only the day's topic/sequence/target expressions plus `overrides: {slot → custom body}` for individually-edited prompts. Editing a *template* changes every non-overridden day.
- **AI is a stub by default** (`AI_PROVIDER=stub`). `shared/ai_client.py` is the only provider seam — the whole three-stage state machine, repetition gate and scoring run offline with no API key and no network. Add a real backend by registering a coroutine in `_PROVIDERS`.

## Admin dashboard (16 sections)

Routes under `/admin/*` (guarded by `<RequireAuth admin>` in `App.tsx`, nav in `AdminLayout.tsx`): Dashboard, Users (`AdminStudents`), Memberships, Verification Queue, Community, Activation Codes, Payments, Book Purchases, Partners, Teachers, Exams & Certification, Orientation (`AdminOrientation`), Videos, Notifications, Reports & Analytics, Archive (super-admin), Activity Logs, Roles & Permissions, Site Links (`AdminSiteLinks` — the public GMB/social URLs).

Student UI: `/dashboard/orientation` + a prompt card on the dashboard home; not a hard gate on the rest of the dashboard. Backend for these lives across the corresponding modules; overview KPIs come from `GET /admin/overview`.
