# SpeakEdge — Project Guide for Claude

The Complete English Communication Ecosystem. API-first **modular monolith**:
FastAPI + MongoDB (Beanie ODM) backend, React + Vite SPA frontend. This file is
the map so you don't need to re-read the whole codebase each session — trust it,
but verify a specific file before editing it (code changes over time).

## Run / build / test

```bash
# Backend (Windows PowerShell) — venv lives at backend/.venv
cd backend; ./.venv/Scripts/python.exe -m uvicorn app.main:app --reload   # or ./run_dev.ps1
cd backend; ./.venv/Scripts/python.exe -m pytest -q                       # tests
cd backend; ./.venv/Scripts/python.exe -m app.db.seed                     # seed admin + demo codes (once)

# Frontend
cd frontend; npm run dev            # vite dev server
cd frontend; npm run build          # tsc -b && vite build  (run this to typecheck)
```

- Always invoke the backend Python via `backend/.venv/Scripts/python.exe` — the base system Python does **not** have the deps (beanie, fastapi, openpyxl…).
- `start.bat` / `stop.bat` at the repo root launch/stop both. Single-service prod: Docker build puts the SPA in `frontend_dist/` and FastAPI serves it (see `backend/app/main.py`).

## Architecture

- **Backend** `backend/app/`
  - `main.py` — app factory; registers every module router under `/api/v1` (see `MODULE_ROUTERS`). Mounts `/media`. Starts the scheduler.
  - `core/` — `config.py` (settings), `envelope.py` (`ok()` response wrapper), `exceptions.py` (typed errors + handlers), `rbac.py` (auth guards), `security.py` (JWT, `Role` enum, password hashing), `cache.py`, `ratelimit.py`.
  - `db/` — `base.py` (`AuditedDocument` base: soft-delete/archive lifecycle + `utcnow()`), `models.py` (**all** Beanie models + enums, ~780 lines — the single source of truth for data shapes), `mongo.py` (init/close), `seed.py`.
  - `modules/<name>/` — each has `router.py` (+ optional `service.py`). One domain per module.
  - `shared/` — `audit.py` (`log_activity`), `email_service.py`, `file_service.py`, `pdf_service.py`, `scheduler.py` (APScheduler: archive purge, scheduled-notification dispatch, orientation reminders), `messaging.py`.
- **Frontend** `frontend/src/`
  - `app/App.tsx` — all routes; `app/layouts/` — `PublicLayout`, `StudentLayout`, `AdminLayout`.
  - `features/<area>/` — page components (`public/`, `auth/`, `dashboard/` = student, `admin/`, `shop/`, `membership/`, `payments/`).
  - `lib/api.ts` — axios instance + `unwrap<T>()` (unwraps envelope, auto-refreshes on 401). `lib/auth.ts` — zustand `useAuth` store (persisted), `Role` type, `isAdmin()`.
  - `features/admin/_shared.tsx` — reusable admin UI kit: `PageHeader`, `StatCard`, `Paginator`, `Modal`, `StatusBadge`/`badgeClass`, `EmptyRow`, `fmtDate`/`rupees`, `downloadExport()` (authenticated blob download for CSV/XLSX).

## Backend conventions

- Every endpoint returns the envelope via `ok(data, message)` from `core/envelope.py`. Frontend unwraps with `unwrap()`.
- Guards from `core/rbac.py`: `require_admin`, `require_super_admin` (super-admin-only: archive restore/purge), `require_student`, `require_examiner`, `require_teacher`, `require_partner`. `require_role(*roles)` builds custom ones; super_admin is always allowed.
- Raise typed errors from `core/exceptions.py`: `NotFoundError`, `ConflictError`, `ValidationAppError`, `ForbiddenError`, `UnauthorizedError` (not raw `HTTPException`).
- Mutating admin actions call `log_activity(actor, action, role=…, target_type=…, target_id=…, meta=…)` (`shared/audit.py`) → visible in the Activity Logs page.
- **Archive-first soft delete**: models subclass `AuditedDocument` (`is_archived`, `archived_at`, `archived_by`, `delete_reason`, `auto_delete_at`). Use `.archive(by, reason)` / `.restore()`. 60-day retention, then the scheduler purges. Most list queries filter `is_archived == False`.
- Add new endpoints to the **existing** module router — don't create new modules casually.
- CSV/XLSX exports: `analytics/router.py` `_export_response(basename, header, rows, fmt)` streams CSV (default) or XLSX (`openpyxl`, in requirements).

## Frontend conventions

- Data fetching: `@tanstack/react-query` (`useQuery`/`useMutation`) + `api`/`unwrap` from `lib/api.ts`. Invalidate queries in `onSuccess`.
- Styling: Tailwind with shared component classes in `styles/index.css` — `card`, `btn-primary`, `btn-gold`, `btn-ghost`, `input`, `label`, `badge`. Brand colors: `brand`, `brand-light`, `brand-gold`, `surface`.
- Icons: `lucide-react` (type icon fields as `LucideIcon`, not a hand-rolled `ComponentType`).
- Admin pages follow the list + filters + detail/action-modal pattern; reuse `_shared.tsx` rather than re-implementing tables/pagination/badges.

## Gotchas (learned the hard way)

- **Beanie serializes the document id as `id`, not `_id`** (`model_dump(mode="json")`, no `by_alias`). In the frontend always read `x.id` for the Mongo id used in action URLs. Using `_id` yields `undefined` → `/undefined/` requests.
- **Notifications router prefix is `/notifications` (plural)**; videos is `/videos` (plural). Most others are singular (`/membership`, `/partner`, `/teacher`, `/exams`, `/community`).
- Notification `recipient` supports `"*"` (all), group keys (`students`/`teachers`/`partners`/`examiners`), or a specific student_id/username. `scheduled_for` set → dispatched later by the scheduler (`sent=False` until then).
- Membership is **lifetime**; the renewable entity is the `Subscription` (`expires_at`). "Renewal" extends the active subscription.
- **Plan pricing (`PlanConfig`)**: checkout charges the **one-time admission/membership fee** (`offer_price` else `amount`) — `service._price_for` returns exactly that. `monthly_fee` is *quoted* on the plan card and collected separately (there is no recurring engine); it is never added to the upfront charge. `prices` (`{month → paise}`) survives only as an optional per-term admin override and seeds **empty**. `months`/`durations` no longer affect price — they only set subscription validity (`_months_to_days`). Other tier dims: `classes_per_week` (teacher-led/week), `conversation_per_week` (= conversation *teams*), `community_years`, `support_years` (student relation support), `cefr_tests`, `speaking_tests`. Spec defaults live in `payments/service.py:PLAN_DEFAULTS`: missing keys are inserted, and rows below `PLAN_SPEC_VERSION` get their spec-owned fields **refreshed once** (bump the constant to push a catalogue revision to a live DB; admin edits stick until the next bump). Scheduler `send_subscription_expiry_reminders` nudges 1 month before expiry.
- **`/plans` (`PlansPage`) is duration-free**: no 3/6/12 tabs. Cards render in a fixed order — `MAIN_ORDER` (Tribe → Basic → Silver → Gold → Diamond), then a separate "More Teacher-Led Learning" section for `PRO_ORDER` (Silver/Gold/Diamond Pro). Plans outside those lists (notably `Basic English Course`, sold under Books) are **not shown**. Monthly fee is the lead price where one exists, admission fee secondary; never combined. Benefit bullets are derived from the `PlanConfig` dims, so admin edits flow through.
- `POST /membership/activate` requires many form fields **and** `photo` + `id_proof` file uploads (multipart). The 5 consent fields are `consent_community_rules`, `consent_terms`, `consent_safety_policy`, `consent_non_refund`, `consent_process` — all still mandatory on the wire, but the learner now ticks **one** combined checkbox: `ActivatePage` (and the admin enroll modal in `AdminCodes`) sets all five from it and disables the submit button until it is ticked. `ACTIVATION_CONSENTS` is now just the list of field names. `whatsapp` is **optional**; `phone` stays required.
- **Policy pages**: `/privacy`, `/terms`, `/faq`, plus `/community-rules`, `/safety-policy`, `/refund-policy` — all in `features/public/LegalPages.tsx`, all linked from the footer and from the activation consent block. Content is drafted from how the platform actually works and still needs a legal review.
- **Public contact + social links live in `frontend/src/lib/site.ts`** (`CONTACT_PHONE`, `WHATSAPP_URL`, `SOCIAL_LINKS`). Social/GMB URLs are empty placeholders; `activeSocialLinks()` filters them out so the footer renders nothing until they're filled in.
- **Free demo** (`/demo` → `POST /leads/demo`): full registration form — name, phone, optional email, **age**, education, occupation, one of three fixed weekly slots, a **preferred date on that slot's weekday**, what they want to improve (optional), attribution, and a **mandatory privacy consent** (`consent_privacy`). All allowlists (`DEMO_SLOTS`, `EDUCATION_OPTIONS`, `OCCUPATION_OPTIONS`, `HEARD_FROM_OPTIONS`) live only in `leads/router.py` and are served by `GET /leads/demo/options` — `DemoPage.tsx` renders whatever that returns, so there is **no list to keep in sync** any more. That endpoint also returns each slot's next `DEMO_DATE_CHOICES` bookable dates, so the date picker can only offer dates the server will accept.
  - The first word of each `DEMO_SLOTS` label is the weekday and is load-bearing — `demo_date` is validated against it. Keep new slots in the same "Weekday time–time" shape.
  - **Dates are IST** (`today_ist()`): using UTC would offer a same-day slot to anyone booking before 05:30 IST.
  - `Lead.demo_group` is **derived from age, never asked** — `demo_group_for_age()` splits at `KIDS_MAX_AGE` (14, inclusive → Kids) and returns `PromptAudience` values so a converted lead lines up with the Kids/Adults course.
  - Everything is shown in Admin → Leads (list + detail modal) and the CSV/XLSX export.
- **Exam slots**: `Exam.scheduled_at` is the bookable date/time. Admin sets it when creating the exam (`POST /exams/` accepts it) or later via assign/edit. Students call `GET /exams/?upcoming=true`, which drops past slots and sorts dated-soonest-first; `GET /exams/my-bookings` is enriched with `exam_title`/`kind`/`scheduled_at` so past slots still render. Booking rejects a past slot and a duplicate booking of the same slot.
- **Monthly fees have no billing engine — only a derived due schedule** (`modules/payments/monthly.py`). Due dates = `Subscription.started_at` + n calendar months (day clamped to short months), while `PlanConfig.monthly_fee > 0` and the date is before `expires_at`. A month is settled by a paid `Payment(kind="monthly", due_month="YYYY-MM")`. `GET /payments/monthly-due` returns the next unsettled month (overdue ones keep coming back) with `reminder_active` true from `REMINDER_DAYS`=3 out; `POST /payments/monthly-order` starts the gateway order. `MonthlyDuePopup` (mounted in `StudentLayout`) shows Due Date + Amount Due + Pay Now and collapses to a persistent bar — never fully dismissible until paid. Scheduler job `send_monthly_payment_reminders` raises one notification per due month (deduped via `Subscription.monthly_reminders_sent`).
- Payments admin actions (`manual-approve`, `refund-status`) key off `razorpay_order_id`; manual/book payments may lack it.
- **Membership + Book is one order, one payment.** Exactly one `BookProduct` carries `is_speakedge_book` (admin ticks it; `book/service.clear_other_speakedge_books` unflags the rest, `GET /books/speakedge` resolves it). That book can only be bought with a plan and vice versa — both entry routes (`/plans` → Subscribe, and `/shop` → SpeakEdge Book → `/plans`) land on `/checkout?plan=`, which posts `plan` (+ a defaulted `months=12` for validity only) to `POST /books/checkout`. The `Payment` stays `kind="book"` (plan + months set) so **no `Subscription` is created at payment**: the plan is stamped on the reserved `ActivationCode` (`plan`, `plan_months`) and `membership/service._start_paid_subscription` turns it into the first Subscription at activation. Guests have no session, so `/payments/verify` (student-only) is not their path — they reconcile via webhook or admin `manual-approve`. Other books keep the plain `/shop/product/:id` flow. `GET /books/receipt/{order_number}?phone=` streams the confirmation PDF (phone must match; rendered on demand, so it works before payment is reconciled).
- Logged-in students on `/plans` still get the book-free renewal path (`startCheckout` → `/payments/order`); only guests are routed through the bundle.
- **Razorpay has two modes, switched by `payments/service.keys_configured()`** (key id starts with `rzp_` and has no `xxxx`). *Demo*: no gateway call, ids are `order_test_*`, `/payments/verify` skips the signature — the frontend mirrors the same rule (`isDemoOrder` in `features/payments/checkout.ts`, `testKeys` in `shop/bookCheckout.ts`) and self-verifies. *Live*: real orders, and a gateway error now **raises** instead of falling back to a test order (a fallback would have been treated as pre-paid). Signature checks are only bypassed for `verify_and_activate(..., trusted=True)`, used by the webhook, whose body HMAC is checked first. `tests/conftest.py` forces demo mode so a real key in `.env` never makes tests hit the network.
- The whole suite passes. `tests/conftest.py` clears the in-memory rate-limit counters before every test — they are process-local, so without it a login-heavy test file 429s an unrelated one.
- **Kids and Adults are separate courses, decided by the activation code.** `ActivationCode.audience` is set by admin at generation (`POST /activation-codes/generate {count, audience}`; `POST /activation-codes/audience` re-points an *unused* code, refused once activated) and is copied to `Student.audience` at activation. `audience` is deliberately **absent from `ProfileUpdate`** in `student_dashboard/router.py` — a student sending it is ignored — so only `PATCH /admin/students/{id}` can move someone between courses. Everything downstream (prompt library `/me/*`, AI sessions) already resolves lessons from `student.audience`. `GET /membership/form-options?code=` is the public lookup that tells the activation form which course a code enrols into.
- **ID proof** is `id_proof_type` (required, allowlisted by `ID_PROOF_TYPES` in `membership/router.py`) + optional `id_proof_number` alongside the existing upload. `ActivatePage.tsx` mirrors the list as `ID_PROOF_TYPES` — keep both in sync. Shown in the verification queue and the admin student profile.
- **Access locks** (`shared/access.py`): `Student.teacher_class_locked` / `community_locked` / `access_lock_reason`, set via `POST /admin/students/{id}/access`. Enforced by the `require_unlocked_teacher_student` / `require_unlocked_community_student` guards, which have **replaced `require_student` throughout `teacher/router.py` and `community/router.py`** — use those guards for any new student endpoint on those surfaces. The two WebSockets authenticate from a query token and so check `_community_locked()` inline instead. A lock is not a suspension: the rest of the account keeps working.
- **The monthly-fee schedule is anchored to `Subscription.billing_start_at`** — the student's first teacher-led class, set by admin via `POST /payments/admin/class-start/{student_id}` (`GET` on the same path returns the current value plus a `suggested_class_start_date` = earliest `Batch.class_dates` entry the student is enrolled in). `monthly.billing_anchor()` falls back to `started_at` when it is unset, so pre-existing subscriptions keep their old dates. Saving a new date clears `monthly_reminders_sent` so reminders re-arm against the new months.
- **No payment can be started without accepting the Terms.** `POST /payments/order` and `POST /books/checkout` both require `accept_terms: true` and stamp `Payment.terms_accepted_at` / `terms_version` (`settings.TERMS_VERSION` — bump it when the policy pages are revised). The monthly-fee order inherits the acceptance from the original purchase rather than asking again. Frontend: `components/TermsAgreement.tsx` exports `TermsAgreement` (inline block for forms — checkout, product page) and `TermsGateModal` (dialog for flows that jump straight to the gateway — plan renewal, accepting a priced offer).
- **The admin prompt library day panel is a local draft with an explicit "Save day" button** — it no longer autosaves on blur. `LineListEditor` keeps blank lines while typing and they are stripped on save. The prompt-body editor keeps its own separate "Save prompt" button.
- **`Video` carries both videos and PDFs** (`kind: "video" | "pdf"`, default `"video"`). Collection is still `videos` and the router is still `/videos`; the student UI splits them (`/dashboard/videos` vs `/dashboard/study-material`) by passing `?kind=`. Membership gating for both lives in `shared/content_access.py` — `modules/video/router.py` imports it under the old private names (`_visible_to_student`, `_student_plan`) so existing tests/imports keep working.
- **Prompt library never materialises 2,880 prompts.** `PromptTemplate` (~10 docs: one per audience × slot) holds the reusable body with `{{placeholders}}`; `PromptLesson` (one per audience/week/day, created lazily) holds only the day's topic/sequence/target expressions plus `overrides: {slot → custom body}` for individually-edited prompts. Editing a *template* changes every non-overridden day.
- **AI is a stub by default** (`AI_PROVIDER=stub`). `shared/ai_client.py` is the only provider seam — the whole three-stage state machine, repetition gate and scoring run offline with no API key and no network. Add a real backend by registering a coroutine in `_PROVIDERS`.

## Prompt Library & AI conversation

- `modules/prompt_library/` — Audience (adults|kids) → Week (1..`PROMPT_WEEKS`=48) → Day (1..`PROMPT_DAYS_PER_WEEK`=6) → 5 slots (`lexical_british|lexical_american|lexical_international|learning|assessment`). `service.render_for_student()` injects CEFR level + preferred English from the `Student` row — prompts are never hand-edited for those. Admin UI: `/admin/prompt-library`. Student read-only UI: `/dashboard/prompt-library` (`PromptLibraryPage`), backed by the three `require_student` GETs `/me/overview`, `/me/day`, `/me/prompt`; every mutating route is `require_admin`. Those two `/me` GETs accept optional `cefr_level` / `preferred_english` — a **render-only preview** (`render_for_student`'s kwargs of the same name) so a student can see how the lesson reads at another level or accent. Nothing is persisted: AI sessions pass neither and always run on the stored profile.
- `modules/ai_session/` — three stages over one `AISession` document. **Stage 1/2 set `awaiting_repetition=True` and refuse to advance the conversation until the student repeats `pending_model_answer`.** Stage 1 injects target collocations; Stages 2 & 3 must not (`service._stage_expressions`). Stage 3 never corrects mid-conversation and only emits `assessment` (6 scores /10) after every `conversation_sequence` step. Student UI: `/dashboard/learning` → `/dashboard/learning/:week/:day/:stage`.
- New `Student` fields drive all of it: `preferred_english`, `preferred_language`, `audience`, `learning_week`, `learning_day` (all defaulted → backward compatible).

## Attendance confirmation & Instructions

- `shared/attendance.py` — 24h before class (`ATTENDANCE_NOTICE_HOURS`) students get a `ClassConfirmation`; 18h later (`ATTENDANCE_DEADLINE_HOURS`) an unanswered one auto-cancels **that student's seat only** (the class still runs). Covers both `Batch` (teacher-led) and `SpeakingTeam` (community) classes. Two scheduler jobs, both idempotent: dedup via `Batch.confirm_notified_dates` + the `ClassConfirmation` row, and via `status != "pending"` + `cancel_notified`. Student UI `/dashboard/attendance`, admin `/admin/attendance`.
- `modules/instructions/` — `Instruction.translations: {lang → {title, body}}`. Resolution order: student's `preferred_language` → the article's `fallback_language` → `DEFAULT_LANGUAGE`. `LANGUAGE_CODES` in `instructions/router.py` is the allowlist the profile endpoint validates against. Shown in the student profile via `InstructionsPanel`; admin at `/admin/instructions`.

## Admin dashboard (16 sections)

Routes under `/admin/*` (guarded by `<RequireAuth admin>` in `App.tsx`, nav in `AdminLayout.tsx`): Dashboard, Users (`AdminStudents`), Memberships, Verification Queue, Community, Activation Codes, Payments, Book Purchases, Partners, Teachers, Exams & Certification, Orientation (`AdminOrientation`), Videos, Notifications, Reports & Analytics, Archive (super-admin), Activity Logs, Roles & Permissions.

**Orientation module** (`modules/orientation/`): one-time new-student onboarding. `OrientationBatch` model (live/recorded sessions, teacher + enrolled `student_ids`); orientation state lives as fields on `Student` (`orientation_status` pending→in_progress→completed, `orientation_batch_id`, `orientation_step`). Single router serves student (`/orientation/me*` — walkthrough + self-complete for recorded sessions), admin (`/orientation/batches*` — CRUD, enrol, mark complete) and teacher (`/orientation/teacher/batches*`) endpoints. Walkthrough content is static in `service.ORIENTATION_STEPS`. Live sessions are completed by the teacher/admin; recorded are self-completable. Batch auto-closes when all enrolled students finish (`service.maybe_close_batch`). Scheduler job `send_orientation_reminders` nudges before live sessions. Student UI: `/dashboard/orientation` + a prompt card on the dashboard home; not a hard gate on the rest of the dashboard. Backend for these lives across the corresponding modules; overview KPIs come from `GET /admin/overview`.
